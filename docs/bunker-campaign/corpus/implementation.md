# Implementation layers for the bunker / zone-clearance feature (T-155B)

Research only. Nothing was launched, cooked, built or measured. Evidence tags: **[proven]** read in a file or a log of this repo, **[inferred]** deduced from headers or bytecode names, **[untested]** needs the game or the editor. `docs/bunker-campaign/corpus/game-systems.md` did not exist when this was written; mechanics are cited from the repo's own research docs instead.

The rule applied (from `public/itr-common/bullet-penetration/README.md`): a one-time Lua write and a cooked Blueprint for per-event logic cost about +0.05 ms, against +0.84 ms for the same logic in Lua on every hit (single runs in that README). "The showcase does it in Lua" is not a reason.

Abbreviations: `DUMP` = `SDK/SDK/IntoTheRadius_classes.hpp` (Dumper-7 of 2.7.2); `T147` = `docs/itr-showcase/t147-framework-design.md`; `NLT` = `docs/itr-showcase/research/native-loading-tides.md`; `SGB` = `docs/itr-showcase/research/sdk-gameplay-bps.md`; `MIS` = `docs/itr-showcase/research/missions.md`.

## 1. Catalogue of layers

### 1.1 Cooked level content (geometry, volumes, nav modifiers, placed actors)

| | |
|---|---|
| Good at | Anything static: the bunker building, basement, doors; `NavModifierVolume` with `NavArea_Null` (cuts the navmesh); `BoxComponent`/trigger volumes; placed stock gameplay BPs (`BP_Bed`, `BP_ShopComputer`, `BP_MonsterSpawner`, `BP_MonsterSpawnGenerator`, `BP_ZoneGate`, `BP_ShelterVolume`, `BP_SpawnBlockingVolume`). The generator places them from JSON (`build_showcase.py` step place; items are `placements.json` records). |
| Runtime cost | Zero for geometry, nav modifiers and volumes (load-time only). A trigger box costs only its overlap events (event-driven; no tick). Unmeasured in this repo; no overlap benchmark exists. A measurement would be a `stat game` comparison with 0 and 200 trigger boxes. Placed gameplay BPs cost what stock ones cost (the T-143 npc-lab BP ticks measured 0.011-0.03 ms per scripted Blueprint per frame under the aiMod ProcessEvent profiler, `build/work/T-143/perf_after.txt`; that is a heavy Tick-driven BP, not an idle placed actor). |
| Build / distribution | Editor run + union cook (about 1.5-10 min), `itr verify` checks, pak in `~mods`. No UE4SS needed for the content itself. The NavArea_Null pattern is already in use for the lake (`v4/lakenav.py`, `build_showcase.py:1145`) [proven in the generator; in-game effect checked by `build_navmesh.py check_nav_strips` on the saved navmesh]. |
| Limits | The navmesh must be re-baked (`itr navmesh`, full editor, gotchas 90) after moving a nav modifier. Stock BPs are used through SDK stand-ins that are not packed (SGB 5, NLT 1.2). Unregistered gameplay tags do not match hierarchically (MIS 2). |
| Reusable by outsiders | Yes, as a pak plus the stand-in method. The `itr-common` example addon and map-making guide cover it. |

### 1.2 Cooked Blueprint paks via BPGen (`ItrShowcaseEditor` plugin)

| | |
|---|---|
| Good at | Per-event logic that only calls Blueprint-callable functions: overlap triggers, timers, branching, spawning, reading/writing Blueprint-visible properties, calling `PRGameData` and interface functions, `SaveGame` slots. Existing precedent: `BP_ItrShowcase_TeleportPad`, `KillVolume`, `PerimeterTide` (child of stock `BP_TideBase`, 0.1 s timer), `MapSettings` (cvars), `Progression`, `CompassSky`, `EggDirector` + `EggSave` (SaveGame, about 530 nodes). Op set: `event`, `custom_event`, `component_event`, `call`, `message` (interface call), `create_delegate`, `get/set`, `branch`, `sequence`, `cast`, `macro` (ForEachLoop etc.), generic `node` escape hatch (`ItrShowcaseBPGen.cpp:457-579`, `SPEC.md`). |
| Runtime cost | The model number: +0.05 ms mean frame at 10 shots/s for the bullet BP vs +0.84 ms Lua (`bullet-penetration/README.md`, single run, 18.47 vs 18.52 ms). A Blueprint reacting to an event costs one VM call per event; a delegate-bound BP event costs nothing between events. T-147 notes that moving loader Lua to BPs bought no measurable time for the once-per-session pieces (T147 (a)); the win is for per-event and per-tick work. |
| Build / distribution | Spec JSON -> editor run (about 1.5 min) -> union cook -> pak. `lint_specs.py` checks specs offline against engine and game headers. Needs the `ItrShowcaseEditor` plugin, the SDK stand-ins and a 4.27 project to author; the finished pak is a plain `~mods` pak with no UE4SS dependency. |
| Limits | BPGen traps are listed in gotchas (pure casts pruned, rebuilding an existing BP with SCS components asserts the editor, `GetConsoleVariableFloatValue` not pure, no `CapsuleComponent` getter, `EndPlay` does not run after a crash). **No op for binding a delegate on another object (`UK2Node_AddDelegate`) exists.** `create_delegate` is only for timer-style signatures and is marked untested in `SPEC.md`; the `node` escape hatch might build an AddDelegate node (untested). Bind-to-`UEventsManager.OnNPCDied` from a BP is therefore the single biggest authoring unknown (see 3 and 4). A BP cannot register hooks, grow config tables or root objects for the GC. |
| Reusable by outsiders | The pak: yes. Authoring needs the plugin (shipped in `public/itr-showcase/project/Plugins/ItrShowcaseEditor`, public) and stubs of the game's C++ classes, which are not redistributable (bullet-penetration README says so). |

### 1.3 Data-asset / data-table changes

| | |
|---|---|
| Good at | Config the game reads at use time: `DA_AmmoConfig.BulletClassActor` (the bullet-penetration write), `MissionNormalConfig` DAs (cooked, used by the missions), `DT_Loot*` tables (own tables), `FLevelConfig` rows, `LevelPoints`, `LevelGates`. |
| Two forms | **One-shot Lua write** after the asset is loaded (and again after a map load): cheap, reversible, no override conflict, but needs UE4SS and a re-apply after a reload (README of bullet-penetration). Level-row, map-centre, gate and loot-table registration are this form (`NativeEnsureRow/Center/Gates`, `RegisterLootTags`; measured about 3 ms and 4 ms once per session, T147 table). **Cooked override** of a stock asset: no UE4SS, but it replaces the whole asset, so two mods collide and a game update can break it (NLT 6.1 open question). |
| Runtime cost | Once per session (load-only). |
| Limits | `TMap`/`TArray` growth from Lua is proven for flat structures (level rows, gates) and untested for nested maps (`LevelPoints`) (MIS 2). `LevelConfigurations` is `BlueprintReadOnly`, so a BP cannot append. Tags written this way stay unregistered; hierarchical tag matching fails, exact matching works (T147 (b)). |
| Reusable by outsiders | Yes: this is the `itr-common` loader's job. |

### 1.4 UE4SS Lua hooks (`RegisterHook`, `NotifyOnNewObject`, `LoopAsync`, key/console handlers)

| | |
|---|---|
| Good at | Anything a Blueprint cannot reach: registering hooks on game UFunctions, key and console handlers, file I/O, JSON, `GameInstance.ReferencedObjects` keep-alive, calling interface functions by address (`TransferToLevel`), reading `BlueprintReadOnly` properties. `RegisterHook` on a Blueprint-implemented or ProcessEvent-dispatched UFunction works (the loader hooks `BP_PhysicsActor_C:OnGrip`, `main.lua:2168`). |
| Runtime cost | Measured in this repo: `FindAllOf`/`FindFirstOf` of a game class 10-14 ms each (T147 table; gotchas 129); static lookups (`GetGameData`, `GetGameModeBase`) 0.00-0.06 ms; the missions keeper at 1 Hz: mean 0.10 ms, with 9 of 183 calls doing a look at mean 2.1 ms, max 11 ms; a Lua-only bullet hook +0.84 ms per frame at 10 shots/s (bullet-penetration README); `GetFullName` scan of about 18,000 referenced objects: 4 s (gotchas 126). A `LoopAsync` poll runs on another thread but `ExecuteInGameThread` puts the work on the game thread. **Per-hook-call and `NotifyOnNewObject` overhead: unmeasured here.** UE4SS docs say `NotifyOnNewObject` fires on every `StaticConstructObject_Internal` of the class or a subclass and warn about registering one class many times ([docs.ue4ss.com NotifyOnNewObject](https://docs.ue4ss.com/lua-api/global-functions/notifyonnewobject.html)); returning true unregisters the callback. A measurement would be: sum `os.clock` deltas over N calls inside a hook (the method `bpen` already uses, gotchas 177; `os.clock` is the only timer, 1 ms resolution). |
| Build / distribution | Edit + `itr deploy` (seconds). Needs UE4SS in the "UE4SS For ITR1" layout (gotchas 177) and a loader mod (`enabled.txt`). Test offline with lua 5.1 and a stub harness. |
| Limits | A native error inside a UE4SS call is not caught by `pcall` and drops the tick (gotchas 126, `Every()` accounting in `main.lua:74`). `HookBeginPlay`, `HookInitGameState`, `HookEngineTick` have crashed or been unavailable (`ue4ss-crash.md`; this build has no `EngineTick`, gotchas 78). Direct C++-to-C++ calls (for example `AMonsterSpawner::SpawnNPC` from native code, `URadiusBulletComponent::ProcessHit`) never reach `ProcessEvent`, so a Lua hook on them never fires (bullet-penetration research 4.1; ScriptHooks.cpp comment). Hooks on `ProcessEvent`-dispatched delegates broadcast do fire (that is how `SphereColliderHit` is reached). |
| Reusable by outsiders | Yes, this is the public layer (the loader and `BPModLoader` ecosystem). Players need UE4SS installed. |

### 1.5 Native C++ in aiMod (`aiMod/`)

| | |
|---|---|
| Good at | Everything, including what Lua cannot: a MinHook detour of `ProcessEvent` (`Main.cpp:133-205`) with a chain (`Setup`, `Noise`, `Telepathy`, `Observe`), and `RegisterScriptHook(Class, Func, handler)` which swaps a Blueprint UFunction's `ExecFunction` to run a C++ handler before the original and can veto it (`ScriptHooks.cpp`; only one use today: `CPP_Char_Mimic_C::Alert` in `Telepathy.cpp:80`). Also reads `GObjects` directly, patches config rows (`Maps.cpp:2792`). |
| Runtime cost | Native speed on the hook; the detour itself runs for every `ProcessEvent` call (aiMod checks the function pointer and passes through). The bench pump runs per ProcessEvent only while `GBenchActive`. aiMod `/perf` exists (game-thread frame stats) but no figure for the hook chain is recorded. Unmeasured. |
| Build / distribution | CMake build, `itr deploy aimod` (blocked while the game runs; DLL locked). aiMod is the repo's dev and test tool; T-141 notes say tooling goes in aiMod, not in the showcase release. It is not part of the public release (`make_release.ps1` ships the pak, loader and UE4SS). |
| Limits | Private DLL; engine-version offsets (`SDK::Offsets::ProcessEvent`); a crash takes the game down. Not usable for "anyone's ITR map". |
| Reusable by outsiders | No. Good for the maintainer's own measurement and for prototyping a hook before it is turned into a BP or Lua. |

### 1.6 Showcase loader / runtime BPs (`build_runtime_bps.py`, `loader_sync.py`, `BP_ItrShowcase_MapSettings`, `runtime.json`)

| | |
|---|---|
| What it is | The loader (`public/itr-showcase/loader/ItrShowcaseLoader`, copy of `itr-common/loader-ue4ss/ITRMapLoader` plus additions) registers the level row, centre, gates, loot tags, grip trigger and exit watch at startup; the data comes from generator outputs (`loader_sync.py` copies `ItrShowcase.loot.json` and writes the `NativeGates` rows and `NativeGenerators` count into `config.lua`; `missions_gen.py` writes `runtime_bps.json`). Three runtime BPs carry per-map values baked from `maps/itrshowcase/runtime.json`: `MapSettings` (cvars set at BeginPlay, restored at EndPlay), `Progression` (player level and trigger flags 2 s after start), `CompassSky`. |

| Build / distribution | `itr deploy showcase-loader` for Lua; BP changes go through editor run + union cook. |
| Limits | `loader_sync.py` and `config.lua` are generated: never hand-edit (gotchas 139). The framework split in T147 (`itr-core`, `itr-missions`, `itr-maploader`) is a proposal, not built. |
| Reusable by outsiders | The generic loader is the reusable part (itr-common). Map-specific data and BPs are examples; the generator's `runtime.json` pattern (generator writes the constants into a BP at build time) is reusable without UE4SS. |

## 3. Per-piece recommendation

Cost classes: zero (nothing at run time), load-only, per-event, per-tick.

| Piece | Cheapest viable layer | Fallback | Cost class | Risks / unknowns |
|---|---|---|---|---|

## 5. Risks and unknowns (short)

1. **BPGen cannot bind `UEventsManager.OnNPCDied`.** No AddDelegate op; `create_delegate` is untested; the `node` escape hatch is untested. Decision between extending the plugin (cost: one C++ op, plugin build under the editor lock) and a one-time Lua hook that forwards a count (per-event, but needs UE4SS).
2. **Whether the native broadcast of `OnNPCDied` is reachable by `RegisterHook`.** Native calls between C++ objects skip `ProcessEvent`. Measure by a hook that logs once.
3. **AI targeting into the safe zone** is not covered by nav cuts; the sight channel is unknown.
4. **Shop, repair and bed in a zone-level context** are untested (only `BP_Bed` spawn seen); `SleepAllowed` is false in the showcase row.
5. **`CustomMarkers` persistence** and **ordering of BeginPlay vs spawner `OnLevelPrepare`** are inferences.
6. **Per-hook and per-delegate cost is unmeasured**; the only measured numbers are the missions keeper, FindAllOf, and the bullet BP vs Lua.
